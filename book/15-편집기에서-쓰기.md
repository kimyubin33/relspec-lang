# 15장. 편집기에서 쓰기

> 이 장에서 배우는 것
> - VS Code에서 `.aha` 파일을 코드처럼 쓰는 법
> - 편집기와 컴파일러가 대화하는 방식: 언어 서버 프로토콜
> - 색칠이 두 층으로 나뉘는 이유: 글자 모양으로 하는 색칠과 뜻으로 하는 색칠
> - 쓰는 도중의 문서를 다루는 방법

이 장의 기능은 AHAA 0.8에서 들어왔고, 본문 속 이름의 색칠은 0.10에서 더해졌습니다. 언어의 문법은 이 장에서 바뀌지 않습니다. 같은 컴파일러를 편집기 안에서 쓰는 방법을 다룹니다.

## 15.1 명령줄에서 편집기로

2장에서는 파일을 저장하고 `aha 검사`를 실행해 결과를 읽었습니다. 이 방식은 고칠 때마다 편집기와 터미널 사이를 오가야 합니다. 편집기에 연결하면 다음이 달라집니다.

| 명령줄 | 편집기 |
| --- | --- |
| 저장하고 명령을 실행해야 오류가 보임 | 글자를 칠 때마다 오류가 그 낱말 아래에 표시됨 |
| 오류의 줄과 열을 읽고 찾아감 | 표시된 곳이 바로 오류의 자리 |
| 목표의 판정은 출력의 맨 아래 | 판정이 그 목표의 줄에 표시됨 |
| 이름이 무엇인지 기억해야 함 | 마우스를 올리면 값과 역할이 보임 |

## 15.2 설치

Rust와 Node.js, VS Code가 필요합니다. 저장소 폴더에서 다음을 실행합니다.

```powershell
cargo build --release --locked
cd editors\vscode
npm.cmd install
```

첫 줄은 컴파일러(`target\release\aha.exe`)를 만들고, 나머지는 확장이 쓰는 라이브러리를 받습니다. PowerShell은 기본 설정에서 `npm`(스크립트 `npm.ps1`)의 실행을 막으므로 `npm.cmd`로 실행합니다. 반드시 `editors\vscode` 폴더 안에서 실행해야 합니다. 다른 폴더에서 실행하면 `package.json`을 찾지 못했다는 오류(`ENOENT`)가 납니다.

그다음 같은 폴더에서 설치 파일(.vsix)을 만들어 설치합니다.

```powershell
npx.cmd --yes @vscode/vsce package --skip-license
code --install-extension ahaa-0.14.0.vsix
```

첫 줄은 VS Code의 공식 패키징 도구(`vsce`)로 `ahaa-0.14.0.vsix`를 만듭니다. 파일 이름의 숫자는 확장의 버전입니다. 둘째 줄에서 `code` 명령을 찾을 수 없다고 나오면, VS Code의 확장 보기에서 `…` 메뉴의 "Install from VSIX…"로 그 파일을 고릅니다.

확장 폴더(`%USERPROFILE%\.vscode\extensions`)에 `editors\vscode`를 직접 복사하는 방법은 쓰지 않습니다. 파일이 맞게 들어가도 VS Code가 확장으로 등록하지 않는 경우가 있었습니다.

VS Code를 다시 시작하고 저장소 폴더를 연 뒤 `.aha` 파일을 엽니다. 창 오른쪽 아래의 언어 표시가 `Plain Text`가 아니라 `AHAA`이면 확장이 동작하는 것입니다. `Plain Text`로 남아 있으면 확장이 설치되지 않은 상태이며, 이때는 색칠도 진단도 나오지 않습니다.

확장은 컴파일러를 다음 순서로 찾습니다.

1. 설정 `aha.server.path`에 적은 경로
2. 열어 둔 폴더의 `target/release/aha`, 그다음 `target/debug/aha`
3. `PATH`에 있는 `aha`

저장소가 아닌 폴더에서 `.aha` 파일을 쓰려면 저장소에서 `cargo install --path . --locked`를 실행해 `aha`를 `PATH`에 설치합니다. 컴파일러를 다시 빌드한 뒤에는 명령 팔레트에서 "AHAA: 언어 서버 다시 시작"을 실행합니다.

## 15.3 편집기가 해 주는 일

다음 파일을 예로 듭니다.

```aha
기준 실험시계: 시간축
대상 유빈
대상 버튼
행위 누르다: 주체, 대상, 시작

정의 지금: 시각 = 실험시계 @ 3 초
미지 반응: 시각 = 실험시계 @ ?

눌림: 유빈이 반응에 버튼을 눌렀다
목표 마감 = 눌림.시작 <= 실험시계 @ 3 초
```

| 기능 | 이 파일에서 |
| --- | --- |
| 색칠 | `기준`, `정의` 같은 선언 낱말, 타입, 수와 단위, 주석이 서로 다른 색으로 보입니다. |
| 진단 | `유빈이`를 지우면 `눌렀다` 아래에 `K504`(주체가 없음)가 바로 표시됩니다. |
| 판정 표시 | 7행에 `미지 '반응': 하한 없음 ~ 3000 밀리초`, 10행에 `목표 '마감': 보장`이 정보로 표시됩니다. 불가능한 목표는 경고로 표시됩니다. |
| 설명 | `지금`에 마우스를 올리면 `정의 지금: 시각 = 3000 밀리초 (실험시계 기준)`, `유빈이`에 올리면 이 문장에서 맡은 역할(주체), `눌렀다`에 올리면 기본형 `누르다`와 필수 역할이 보입니다. |
| 정의로 이동 | `유빈이`에서 `대상 유빈` 줄로, `눌렀다`에서 `행위 누르다` 줄로, `(참조 1)`에서 `참조 1:` 줄로 갑니다. |
| 자동 완성 | 선언 낱말, 타입, 단위, 이 파일에서 선언한 이름을 제안합니다. |
| 개요 | 선언한 이름과 참조, 이름 붙은 문장의 목록을 보여 줍니다. |
| 연결망 | 편집기 오른쪽 위의 아이콘이나 "AHAA: 연결망 보기" 명령으로, 이 파일의 연결망을 옆에 엽니다(18장). |
| 줄바꿈 | `.aha` 파일에서는 자동 줄바꿈이 켜져, 긴 줄이 창 밖으로 넘어가지 않습니다. |

판정을 "정보"로 표시하는 것은 AHAA에 고유한 쓰임입니다. 보통의 언어에서 편집기 진단은 잘못된 곳을 알리는 데 쓰입니다. AHAA에서는 컴파일의 결과가 실행 파일이 아니라 판정이므로, 그 판정을 원인이 된 줄에 붙여 보여 줍니다.

## 15.4 이론: 언어 서버 프로토콜

### M × N 문제

편집기가 M개, 언어가 N개 있다고 합시다. 편집기마다 언어마다 따로 지원을 만들면 M × N개의 구현이 필요합니다. 편집기와 언어 사이에 공통의 약속을 하나 두면, 편집기는 그 약속을 한 번만 구현하고 언어도 한 번만 구현하면 됩니다. 필요한 구현은 M + N개로 줄어듭니다.

이 약속이 **언어 서버 프로토콜**(Language Server Protocol, LSP)입니다. Microsoft가 VS Code를 만들면서 정리해 2016년에 공개했고, 지금은 대부분의 편집기가 지원합니다. AHAA의 언어 서버는 `aha lsp` 명령이며, VS Code 확장은 이 명령을 실행하고 연결하는 일만 합니다. LSP를 지원하는 다른 편집기에서도 `aha lsp`를 실행하도록 설정하면 같은 기능을 쓸 수 있습니다.

### 대화의 모양

편집기(클라이언트)와 언어 서버는 서로 다른 프로그램입니다. 둘은 **JSON-RPC 2.0** 형식의 메시지를 표준 입출력으로 주고받습니다. 메시지 하나는 길이를 알리는 머리글과 JSON 본문으로 이루어집니다.

```text
Content-Length: 132

{"jsonrpc":"2.0","id":7,"method":"textDocument/hover",
 "params":{"textDocument":{"uri":"file:///예제.aha"},"position":{"line":5,"character":4}}}
```

메시지는 세 종류입니다.

| 종류 | 특징 | 예 |
| --- | --- | --- |
| 요청 | `id`가 있고, 받은 쪽이 같은 `id`로 답해야 함 | `textDocument/hover`: 이 위치의 설명을 달라 |
| 응답 | 요청의 `id`와 결과 또는 오류 | 설명 글 |
| 알림 | `id`가 없고 답하지 않음 | `textDocument/didChange`: 문서가 바뀌었다 |

문서를 고치는 흐름은 다음과 같습니다.

```text
편집기                               aha lsp
  │── didChange (문서 전체) ────────▶ │  컴파일
  │◀──── publishDiagnostics ───────── │  오류 또는 판정
  │── hover (5행 4열) ──────────────▶ │
  │◀──── "정의 지금: 시각 = ..." ──── │
```

AHAA의 서버는 문서가 바뀔 때마다 문서 전체를 받습니다(전체 동기화). 바뀐 부분만 받는 방식도 있지만, `.aha` 파일은 작고 컴파일이 빠르므로 단순한 쪽을 택했습니다.

### 위치를 세는 단위

LSP에서 위치는 (줄, 줄 안의 자리)이며 둘 다 0부터 셉니다. 줄 안의 자리는 글자 수가 아니라 **UTF-16 코드 단위**로 셉니다. 한글은 한 글자가 한 단위이지만, 일부 이모지는 두 단위입니다. 2장에서 컴파일러의 열 번호를 UTF-16으로 센다고 한 것이 여기서 쓰입니다. 컴파일러의 열(1부터)에서 1을 빼면 그대로 LSP의 자리가 됩니다.

## 15.5 이론: 두 층의 색칠

색칠은 두 층으로 이루어집니다.

**첫째 층은 글자 모양으로 합니다.** VS Code는 TextMate 문법이라는 형식을 씁니다. 줄마다 정규식을 적용해 맞는 부분에 종류를 붙이는 방식입니다. 예를 들어 "줄의 처음에 `정의`가 있으면 선언 낱말"이라는 규칙입니다. 컴파일러 없이 동작하므로 오류가 있는 문서에서도 색이 나오고 매우 빠릅니다.

그런데 정규식은 글자의 모양만 봅니다. 다음 문장을 봅시다.

```text
유빈이 버튼을 눌렀다
```

`유빈이`는 대상 `유빈`에 조사 `이`가 붙은 것일 수도 있고, `유빈이`라는 이름 자체일 수도 있습니다. 어느 쪽인지는 무엇이 선언되어 있는지를 알아야 정해집니다(8장). 이것은 모양이 아니라 뜻의 문제이므로 정규식으로는 풀 수 없습니다.

**둘째 층은 뜻으로 합니다.** 컴파일러는 어떤 낱말이 선언한 이름인지 압니다. LSP에는 서버가 "이 자리부터 이 길이까지는 변수"라고 알려 주는 **의미 토큰**(semantic tokens)이라는 기능이 있고, 편집기는 이것을 첫째 층 위에 덧칠합니다. AHAA는 0.10부터 본문 속의 선언한 이름을 이 방법으로 색칠합니다(17장).

```aha
단위 원
정의 기본요금 = 3만 원
대상 신청자
본문: 신청자는 기본요금을 먼저 낸다
```

4행의 글은 첫째 층에서는 통째로 "글"입니다. 둘째 층에서 `신청자`와 `기본요금`이 이름의 색으로 바뀝니다. 뒤에 붙은 `는`과 `을`은 색칠되지 않습니다.

의미 토큰은 다음 형식의 수 다섯 개를 이름마다 보냅니다. 위치를 앞 토큰과의 차이로 적어 메시지를 줄이는 방식입니다.

```text
줄의 차이, 자리의 차이(같은 줄일 때), 길이, 종류, 수식
```

| 층 | 근거 | 장점 | 한계 |
| --- | --- | --- | --- |
| TextMate 문법 | 글자의 모양(정규식) | 컴파일러가 필요 없고 항상 동작 | 선언을 모름 |
| 의미 토큰 | 컴파일 결과 | 선언한 이름을 정확히 앎 | 컴파일에 성공해야 갱신됨 |

## 15.6 쓰는 도중의 문서

편집기에서 문서는 대부분의 시간 동안 미완성입니다. `정의 가: 정수 =`까지 친 순간에도 서버는 그 문서를 받습니다. 그래서 서버에는 명령줄에는 없던 요구가 생깁니다.

**멈추지 않아야 합니다.** 컴파일러가 어떤 입력에서 비정상 종료하면 편집기의 모든 기능이 사라집니다. 저장소의 `tests/robustness.rs`는 예제와 이 책의 모든 예제를 글자 하나씩 쳐 나가는 중간 상태로 만들어(1만 개 이상) 컴파일러가 멈추지 않는지 확인합니다. 그래도 남을 수 있는 경우에 대비해, 서버는 컴파일러가 멈추더라도 그 요청만 실패로 처리하고 계속 돕니다.

**오류가 있어도 도와야 합니다.** AHAA 컴파일러는 첫 오류에서 멈춥니다(부록 C). 그러면 오류가 하나라도 있는 동안에는 이름의 목록을 알 수 없게 됩니다. 그래서 개요와 자동 완성은 컴파일 결과가 아니라 줄의 앞머리만 읽어서 만듭니다. `대상 유빈`으로 시작하는 줄이 있으면, 파일의 다른 곳에 오류가 있어도 `유빈`이 선언되었다고 봅니다. 설명과 색칠은 마지막으로 컴파일에 성공했을 때의 내용을 유지합니다.

| 기능 | 근거 | 오류가 있을 때 |
| --- | --- | --- |
| 진단 | 지금의 컴파일 | 첫 오류 하나를 표시 |
| 개요, 자동 완성, 정의로 이동 | 줄의 앞머리 | 동작 |
| 설명, 판정 표시, 본문 속 이름의 색칠 | 마지막으로 성공한 컴파일 | 이전 내용 유지 |

## 15.7 알려진 한계

- 오류는 한 번에 하나만 표시됩니다. 여러 오류를 한 번에 보고하려면 컴파일러가 오류 뒤에도 계속 읽을 수 있어야 하며(오류 복구), 앞으로의 과제입니다.
- 문장 안의 이름(`유빈이`)은 아직 색칠하지 않습니다. 본문 속의 이름만 색칠합니다.
- 이름 바꾸기와 "이 이름을 쓰는 곳 찾기"는 없습니다.
- Visual Studio(VS Code가 아닌 IDE)용 확장은 없습니다.

## 연습 문제

**1.** 편집기 5개와 언어 20개가 있습니다. 공통 프로토콜이 없을 때와 있을 때 필요한 구현의 수를 구하세요.

<details>
<summary>풀이</summary>

없을 때는 5 × 20 = 100개, 있을 때는 5 + 20 = 25개입니다.

</details>

**2.** `대상 유빈` 줄을 `대상 유` 까지만 친 상태에서, 파일 아래쪽의 `유빈이 버튼을 눌렀다`에는 어떤 진단이 나오겠습니까? 그리고 그때 개요에는 무엇이 보이겠습니까?

<details>
<summary>풀이</summary>

`유빈`이 선언되지 않았으므로 문장의 `유빈이`에서 `K501`(알 수 없는 낱말)이 나옵니다. 개요는 줄의 앞머리만 읽으므로 `유`라는 대상과 나머지 선언들이 보입니다.

</details>

**3.** `유빈이`를 TextMate 문법만으로 "이름 + 조사"로 색칠할 수 없는 이유를 한 문장으로 설명하세요.

<details>
<summary>풀이</summary>

`유빈`과 `유빈이` 중 어느 것이 선언된 이름인지는 파일의 다른 줄에 달려 있는데, 정규식은 그 줄의 글자 모양만 보기 때문입니다.

</details>
