# 12장. 중간 표현(JSON)

> 이 장에서 배우는 것
> - `컴파일` 명령이 출력하는 JSON의 모든 항목
> - 식의 나무가 JSON으로 어떻게 기록되는가
> - 다른 도구에서 이 출력을 읽을 때의 규칙

이 장은 RelSpec 0.7의 출력을 기준으로 합니다.

## 12.1 중간 표현이란

컴파일러는 소스를 읽어 검사한 뒤, 그 결과를 **중간 표현**(intermediate representation, IR)으로 만듭니다. 소스는 사람이 읽기 위한 형식이고, 중간 표현은 프로그램이 읽기 위한 형식입니다. RelSpec은 중간 표현을 JSON으로 출력하므로, 편집기 확장, 시각화 도구, 다른 언어로 만든 프로그램이 RelSpec 명세를 그대로 가져다 쓸 수 있습니다.

```powershell
cargo run --locked -- 컴파일 "./examples/첫파일.kpl"
```

## 12.2 전체 구조

이 장에서는 다음 파일 하나로 모든 항목을 설명합니다.

```kpl
기준 시계: 시간축
대상 유빈
대상 공
정의 시작: 시각 = 시계 @ 1 초
사건 던짐: 주체 = 유빈, 대상 = 공, 시작 = 시작
미지 반응: 시각 = 시계 @ ?
조건 뒤 = 반응 >= 던짐.시작
관측 반응 = 시계 @ 1200 밀리초
목표 빠름 = 반응 - 던짐.시작 <= 300 밀리초
검사 확인 = 던짐.시작 == 시작 그리고 아님 거짓
행위 잡다: 주체, 대상
잡음: 유빈이 반응에 공을 70% 이렇게 잡았다 (참조 1)
참조 1: 두 손으로
```

최상위 객체의 항목은 다음과 같습니다.

| 항목 | 내용 | 항상 있음 |
| --- | --- | --- |
| `languageVersion` | 언어 버전 문자열 (`"0.7"`) | 예 |
| `statements` | 정의와 검사 | 예 |
| `frames` | 기준 | 아니요 |
| `entities` | 대상 | 아니요 |
| `events` | `사건` 선언 | 아니요 |
| `unknowns` | 미지값과 그 범위 | 아니요 |
| `constraints` | 조건과 관측 | 아니요 |
| `goals` | 목표와 판정 | 아니요 |
| `verbs` | 행위 선언 | 아니요 |
| `sentences` | 문장 | 아니요 |
| `references` | 참조 본문 | 아니요 |
| `rules` | 규칙과 결론의 정도 | 아니요 |
| `conditionals` | 문장으로 쓴 규칙(조건문) | 아니요 |

"항상 있음"이 아니요인 항목은 내용이 비어 있으면 아예 출력하지 않습니다. 그래서 새 기능을 쓰지 않는 파일의 출력은 이전 버전과 버전 문자열만 다르고 나머지가 같습니다. 이것이 버전이 올라가도 기존 도구가 깨지지 않게 하는 **하위 호환성**의 장치입니다.

## 12.3 공통 규칙

- **수는 문자열입니다.** `"value": "1000"`처럼 수도 문자열로 기록합니다. RelSpec의 정수에는 크기 제한이 없는데(3장), JSON을 읽는 많은 프로그램은 수를 64비트 부동소수점으로 읽어 2⁵³을 넘는 정수를 정확히 다루지 못합니다. 문자열로 두면 읽는 쪽이 큰 정수 라이브러리로 정확히 바꿀 수 있습니다.
- **값은 기본 단위입니다.** 시간·시각은 밀리초, 거리·위치는 밀리미터이며, `unit` 항목에 단위 이름이 있습니다.
- **기준 위의 값에는 `frame`이 있습니다.** 시각·위치 값에만 붙습니다.
- **타입 이름은 한국어입니다.** `"type": "시각"`처럼 소스에서 쓰는 타입 이름을 그대로 씁니다. 문장의 지시어 역할에는 타입 대신 `"참조"`가 들어갑니다.
- **논리값은 `"참"`, `"거짓"`**, 정도는 `"70%"`나 `"16.5%"`, 대상은 대상 이름입니다.
- **규칙의 방식에 따라 갈라지는 값**은 `"56%~70%"`(정도의 범위)나 `"거짓|참"`으로 적고, 조합마다의 값을 `outcomes`에 따로 기록합니다(12.12).
- **미지값이 든 값**은 `"반응 + 200"`처럼 미지값 이름이 들어간 식으로 적습니다.

## 12.4 statements: 정의와 검사

```text
{
  "kind": "정의",
  "name": "시작",
  "type": "시각",
  "value": "1000",
  "unit": "밀리초",
  "frame": "시계",
  "expression": { ... }
}
```

| 항목 | 내용 |
| --- | --- |
| `kind` | `"정의"` 또는 `"검사"` |
| `name` | 이름 |
| `type` | 값의 타입. 검사는 항상 `"논리"` |
| `value` | 계산된 값. 통과한 검사는 항상 `"참"` |
| `unit` | 단위 (시간·거리·시각·위치일 때) |
| `frame` | 기준 이름 (시각·위치일 때) |
| `outcomes` | 값이 규칙의 방식에 따라 갈라질 때만 있음 (12.12) |
| `expression` | 식의 나무 (12.5) |

미지값이 들어간 검사도 여기에 `"참"`으로 기록됩니다. 모든 해에서 보장되어야 통과하기 때문입니다(7장).

## 12.5 expression: 식의 나무

4장에서 식은 나무라고 했습니다. JSON에서는 각 마디가 객체이고, `kind`가 마디의 종류입니다. 모든 마디에는 그 마디의 결과 타입 `type`이 있습니다.

| `kind` | 뜻 | 추가 항목 |
| --- | --- | --- |
| `literal` | 리터럴 | `value`, `unit`(있으면) |
| `reference` | 이름 참조 | `name` |
| `unary` | 단항 연산 | `operator`, `operands`(1개) |
| `binary` | 이항 연산 | `operator`, `operands`(2개) |
| `anchor` | `기준 @ 값` | `frame`, `operands`(1개) |
| `member` | `사건.역할` | `event`, `role` |

예제의 `검사 확인 = 던짐.시작 == 시작 그리고 아님 거짓`은 다음 나무가 됩니다.

```text
binary 그리고 (논리)
├── binary == (논리)
│   ├── member 던짐.시작 (시각)
│   └── reference 시작 (시각)
└── unary 아님 (논리)
    └── literal 거짓 (논리)
```

```text
{
  "kind": "binary", "type": "논리", "operator": "그리고",
  "operands": [
    { "kind": "binary", "type": "논리", "operator": "==",
      "operands": [
        { "kind": "member", "type": "시각", "event": "던짐", "role": "시작" },
        { "kind": "reference", "type": "시각", "name": "시작" } ] },
    { "kind": "unary", "type": "논리", "operator": "아님",
      "operands": [ { "kind": "literal", "type": "논리", "value": "거짓" } ] } ]
}
```

리터럴의 `value`도 기본 단위로 바뀌어 있습니다. `1 초`는 `"value": "1000", "unit": "밀리초"`입니다.

## 12.6 frames, entities

```text
"frames":   [ { "name": "시계", "axis": "시간축" } ]
"entities": [ { "name": "유빈" }, { "name": "공" } ]
```

`axis`는 `"시간축"` 또는 `"위치축"`입니다. 둘 다 선언한 순서대로 나옵니다.

## 12.7 events: 사건 선언

```text
{
  "name": "던짐",
  "roles": [
    { "role": "주체", "type": "대상", "value": "유빈", "expression": { ... } },
    { "role": "대상", "type": "대상", "value": "공", "expression": { ... } },
    { "role": "시작", "type": "시각", "value": "1000", "unit": "밀리초", "frame": "시계", "expression": { ... } },
    { "role": "종료", "type": "시각", "value": "1000", "unit": "밀리초", "frame": "시계" }
  ]
}
```

역할은 적은 순서대로 나옵니다. `종료`를 생략한 사건에는 시작과 같은 값의 `종료`가 마지막에 덧붙고, 소스에 식이 없으므로 `expression`이 없습니다. 읽는 쪽은 `expression`의 유무로 "직접 적은 역할"과 "기본값으로 채운 역할"을 구분할 수 있습니다.

## 12.8 unknowns: 미지값

```text
{ "name": "반응", "type": "시각", "unit": "밀리초", "frame": "시계",
  "min": "1200", "max": "1200", "observed": "1200" }
```

| 항목 | 내용 |
| --- | --- |
| `min`, `max` | 모든 조건과 관측을 만족하는 해에서의 최솟값·최댓값. 경계가 없으면 `null` |
| `observed` | 관측했으면 그 값. 관측하지 않았으면 항목이 없음 |

`min`과 `max`는 `null`이어도 항목 자체는 항상 있습니다. "경계 없음"도 판정 결과의 일부이기 때문입니다.

## 12.9 constraints: 조건과 관측

```text
{ "kind": "조건", "name": "뒤", "expression": { ... } }
{ "kind": "관측", "name": "반응", "expression": { ... } }
```

`kind`가 `"관측"`이면 `name`은 관측한 미지값의 이름이고, `expression`은 관측값의 식입니다. 조건과 관측을 한 목록에 두되 종류를 구분하는 것은, 둘 다 해 집합을 좁히지만 하나는 규칙이고 하나는 측정이라는 7장의 구분을 그대로 남기기 위해서입니다.

## 12.10 goals: 목표

```text
{ "name": "빠름", "status": "보장", "missingObservations": [], "expression": { ... } }
```

| 항목 | 내용 |
| --- | --- |
| `status` | `"보장"`, `"가능"`, `"불가능"` |
| `missingObservations` | `가능`일 때 목표에 등장하는 미지값 중 아직 관측하지 않았고 조건만으로 값이 정해지지도 않은 것. 다른 판정에서는 빈 목록 |
| `undecidedRules` | `가능`일 때 계산 방식에 따라 판정을 가르는 규칙의 이름. 비어 있으면 항목이 없음 |

## 12.11 verbs, sentences, references

```text
"verbs": [ { "name": "잡다", "required": ["주체", "대상"] } ]
```

`required`에는 선언에 적지 않았어도 항상 `주체`가 들어 있습니다. 활용형을 괄호로 적었으면 `forms` 목록이 추가됩니다.

```text
{
  "line": 12, "label": "잡음", "verb": "잡다", "form": "잡았다",
  "degree": 70, "tense": "과거",
  "roles": [
    { "role": "주체", "particle": "이", "type": "대상", "value": "유빈" },
    { "role": "시작", "particle": "에", "type": "시각", "value": "반응", "unit": "밀리초", "frame": "시계" },
    { "role": "대상", "particle": "을", "type": "대상", "value": "공" },
    { "role": "방식", "particle": "", "type": "참조", "value": "참조 1", "reference": 1 }
  ],
  "references": [1]
}
```

| 항목 | 내용 |
| --- | --- |
| `line` | 소스의 줄 번호 |
| `label` | `이름:`을 붙였으면 그 이름 |
| `verb`, `form` | 행위의 기본형과 문장에 쓰인 활용형 |
| `degree` | 정도(정수 퍼센트). 이것만 문자열이 아니라 수입니다(0~100이므로) |
| `tense` | `"과거"`, `"현재"`, `"미래"`. 기본형이면 없음 |
| `roles` | 문장에 나온 순서대로의 역할. `particle`은 실제로 쓴 조사(지시 부사는 빈 문자열) |
| `references` | 문장 끝에서 인용한 참조 번호 |

이 예에서 시작 역할의 값이 `"반응"`인 것은 미지값을 썼기 때문입니다. 지시어가 채운 역할에는 `reference`에 참조 번호가 있습니다.

```text
"references": [ { "number": 1, "text": "두 손으로" } ]
```

## 12.12 rules와 outcomes

13장의 규칙은 `rules`에 기록됩니다.

```kpl
대상 컵
행위 떨어지다: 주체
떨어짐: 컵이 70% 떨어졌다
규칙 깨짐: 떨어짐 이면 80%
규칙 확정: 떨어짐 이면 80% 곱으로
정의 공존: 정도 = 깨짐 그리고 아님 깨짐
목표 한쪽만 = 깨짐 >= 60%
```

```text
"rules": [
  { "name": "깨짐", "premise": { ... }, "strength": { ... }, "value": "56%~70%",
    "outcomes": [
      { "choices": { "깨짐": "최소" }, "value": "70%" },
      { "choices": { "깨짐": "곱" }, "value": "56%" } ] },
  { "name": "확정", "method": "곱", "premise": { ... }, "strength": { ... }, "value": "56%" }
]
```

| 항목 | 내용 |
| --- | --- |
| `name` | 규칙의 이름 |
| `method` | `"최소"` 또는 `"곱"`. 방식을 정하지 않았으면 항목이 없음 |
| `premise`, `strength` | 전제와 강도의 식 (12.5) |
| `value` | 결론의 정도. 방식에 따라 갈라지면 `"56%~70%"`처럼 가장 작은 값과 가장 큰 값 |
| `outcomes` | 값이 갈라질 때만 있음 |

`outcomes`의 각 항목은 방식의 조합 하나(13장의 세계 하나)입니다. `choices`는 "방식을 정하지 않은 규칙의 이름 → 그 세계에서 고른 방식"이고, `value`는 그 세계에서의 값입니다. 같은 구조가 갈라지는 값을 가진 `정의`에도 붙습니다.

```text
{ "kind": "정의", "name": "공존", "type": "정도", "value": "30%~44%",
  "outcomes": [
    { "choices": { "깨짐": "최소" }, "value": "30%" },
    { "choices": { "깨짐": "곱" }, "value": "44%" } ],
  "expression": { ... } }
```

목표에는 판정을 가르는 규칙이 기록됩니다.

```text
{ "name": "한쪽만", "status": "가능", "missingObservations": [], "undecidedRules": ["깨짐"], "expression": { ... } }
```

## 12.13 conditionals

14장의 조건문은 `sentences`가 아니라 `conditionals`에 기록됩니다.

```kpl
대상 컵
행위 떨어지다: 주체
행위 깨지다: 주체
컵이 70% 떨어졌다
깨짐: 컵이 떨어지면 컵이 80% 깨진다
```

```text
{
  "line": 5, "name": "깨짐", "labeled": true,
  "condition": { "verb": "떨어지다", "form": "떨어지면",
                 "roles": [ { "role": "주체", "particle": "이", "type": "대상", "value": "컵" } ] },
  "matchedLines": [4],
  "premise": "70%",
  "strength": "80%",
  "conclusion": { "verb": "깨지다", "form": "깨진다",
                  "roles": [ { "role": "주체", "particle": "이", "type": "대상", "value": "컵" } ] },
  "value": "56%~70%",
  "outcomes": [
    { "choices": { "깨짐": "최소" }, "value": "70%" },
    { "choices": { "깨짐": "곱" }, "value": "56%" } ]
}
```

| 항목 | 내용 |
| --- | --- |
| `line` | 소스의 줄 번호 |
| `name` | 조건문에 붙인 이름. 붙이지 않았으면 `"5행"`처럼 줄 번호 |
| `labeled` | 이름을 붙였는지 |
| `method` | `"최소"` 또는 `"곱"`. 정하지 않았으면 항목이 없음 |
| `condition`, `conclusion` | 전제와 결론의 절: 행위의 기본형(`verb`), 쓰인 꼴(`form`), 역할(`roles`, 12.11과 같은 구조) |
| `matchedLines` | 전제에 해당한 사실이 적힌 줄. 조건문이 이끌어 낸 사실이면 그 조건문의 줄 |
| `premise` | 전제의 정도. 해당한 사실들의 정도 가운데 최댓값 |
| `strength` | 규칙의 강도. 결론에 적은 정도이며 적지 않았으면 `"100%"` |
| `value` | 결론의 정도 |
| `outcomes` | 값이 방식에 따라 갈라질 때만 있음 (12.12) |
| `references` | 인용한 참조 번호. 없으면 항목이 없음 |

`matchedLines`를 따라가면 어떤 사실에서 어떤 결론이 나왔는지, 추론의 경로를 되짚을 수 있습니다.

## 12.14 읽는 쪽을 위한 조언

- `languageVersion`을 먼저 확인하세요. 모르는 버전이면 경고하는 것이 안전합니다.
- 모르는 항목은 무시하세요. 이후 버전에서 항목이 늘어날 수 있습니다.
- 수는 문자열이므로 큰 정수 라이브러리로 바꾸세요.
- 출력은 검사를 통과한 프로그램에 대해서만 나옵니다. 오류가 있으면 JSON 대신 진단이 표준 오류로 나오고 종료 코드가 1입니다(2장).

## 정리

- `컴파일`은 검사를 통과한 명세를 JSON 중간 표현으로 출력합니다.
- 수는 문자열, 값은 기본 단위, 기준 위의 값에는 `frame`이 붙습니다.
- 식은 `kind`로 구분되는 마디의 나무입니다.
- 새 기능의 항목은 비어 있으면 출력하지 않아 하위 호환성을 지킵니다.

## 연습 문제

1. `정의 가: 거리 = 2 미터 + 5 센티미터`를 컴파일하면 `statements[0]`의 `value`, `unit`, 그리고 `expression`의 뿌리 마디는 어떻게 될까요?
2. 수를 문자열로 기록하지 않으면 어떤 문제가 생길 수 있는지 3장의 큰수 예제로 설명해 보세요.

<details>
<summary>풀이</summary>

1. `value`는 `"2050"`, `unit`은 `"밀리미터"`이고, 뿌리 마디는 `{"kind": "binary", "type": "거리", "operator": "+", ...}`이며 두 자식은 `"2000"`과 `"50"` 리터럴입니다.
2. 3장의 큰수는 39자리 정수입니다. JSON을 64비트 부동소수점으로 읽는 프로그램은 2⁵³(약 9×10¹⁵)을 넘는 정수의 아래 자릿수를 잃어 다른 수로 읽습니다. 문자열이면 자릿수가 그대로 보존됩니다.

```kpl
정의 가: 거리 = 2 미터 + 5 센티미터
검사 확인 = 가 == 2050 밀리미터
```
